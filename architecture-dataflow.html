Applicant Secure Token

Applications get a UUID secure_token at creation. Applicants use this (not a login) to upload documents, check status, and respond to info requests. secure-token.js middleware validates and attaches the application to the request.

AI Evaluation Pipeline

Two-phase: Foundry agent validation → rules-based credit engine

Phase 1 — Foundry Agent Validation
AGENT Azure Foundry called

INSERT ai_evaluations { status='pending' } → UPDATE applications status='under_evaluation'

Tool: verify_courses

Checks institution accreditation, course existence in catalog, transcript data completeness

❌ FAIL path

UPDATE ai_evaluations status='failed' → UPDATE applications status='information_required' → INSERT information_requests → Email student → STOP

✅ PASS path

Continues to Phase 2 credit engine evaluation

Phase 2 — Credit Engine (engine.js v1.1.0)

Pure stateless function — runs for every transcript_course in sequence

RULE Eligibility Check

grade < C → REJECTED (R1) · W grade → WITHDRAW · quarter system → credits × ⅔ (R2)

KB Equivalency Lookup

SELECT equivalencies WHERE institution=X AND course=Y → if found: outcome='transfer', confidence=HIGH, skip remaining steps

KB Precedent Lookup

SELECT past_decisions WHERE institution=X AND course≈Y → if found: outcome from precedent, path='precedent'

TF-IDF BU Catalog Match

Vectorise: title + description + learning_outcomes → cosine similarity against BU catalog → top-N candidates with scores

RULE Policy Rules R1–R10

Apply caps, substitutions, exclusions, BU-only courses, major requirements, quarter conversion

INSERT course_evaluations

path (transfer|elective|no_credit) · award (BU course) · bu_credits · confidence · rules[] · candidates JSONB · reasons JSONB

AGENT Foundry Phase 2 (unresolved courses)

search_precedents + search_bu_catalog tool calls → additional recommendations merged into course_evaluations

UPDATE ai_evaluations + applications

status='completed' · UPDATE applications status='evaluation_completed'

Application Lifecycle

From transcript upload to credit posted — every step the agent evaluation pipeline takes.

Everything starts with a transcript — either uploaded via the portal or arriving by email. The transcript is parsed into structured course data and saved to Supabase. Then the Agent Evaluation Pipeline kicks in: Phase 1 is the internal credit engine (rules-based, KB-driven, TF-IDF similarity), Phase 2 is the Azure AI agent (validates the institution, then fills in anything the engine left unresolved). Courses the pipeline can't settle go to a human evaluator. The Credit Office posts final credits and the knowledge base is updated for next time.

1
Transcript Arrives
Two entry paths — student uploads via the secure portal link, or a transcript email arrives in the configured inbox.
→

Portal upload: Student uses their personal secure link (no login required) to attach the PDF transcript

→

Email path: IMAP poller watches the inbox, extracts PDF attachments, and creates the application automatically

→

Raw PDF saved to Supabase Storage

→

Application record created in Supabase

2
Transcript Parsed into Courses
The PDF is read and each course is extracted into a structured record.
→

→

Pulls out: institution, course code, title, grade, credits, credit system (semester / quarter), term

→

Each course saved to Supabase — one record per course

→

Quality flags checked: missing credits, unreadable grades, repeated courses

3

→

→

→

Agent Evaluation Pipeline triggered immediately in the background — non-blocking, no queue or delay

Agent Evaluation Pipeline — runs in background
4
Agent Evaluation Pipeline — Credit Engine PHASE 1
The internal rules-based engine runs first on every course. It loads the BU catalog, equivalency knowledge base, and past decisions from Supabase, builds a TF-IDF index, then works through each course in order.
1

Grade check — Below C or withdrawn? Mark as no credit and skip. Stop for this course.

2

Equivalency lookup KB — Exact match in the equivalency knowledge base? Outcome set instantly, confidence = 1.0. No human needed.

3

Past decisions lookup KB — Same course decided before? Use that outcome, confidence = 0.9.

4

TF-IDF similarity match — Vectorise course title + description + learning outcomes, cosine-compare against the BU catalog. Returns top 3 candidates. Threshold: 0.25 similarity.

5

Policy rules — Quarter unit conversion, BU-only courses (elective credit only), econ upper-level cap, CS major substitutions, repeat course handling.

→

Evaluation results saved to Supabase: path taken, outcome, confidence, top match candidates, reasons

✓ Resolved by engine
Equivalency or policy rule settled it. No agent or human needed.
⚠ Unresolved
Similarity match or incomplete data. Passed to the AI agent next.
5
Agent Evaluation Pipeline — AI Review PHASE 2
The Azure AI Foundry agent runs after the credit engine — only if configured. Two phases: first it validates institution and course data, then it fills in recommendations for anything the engine left unresolved.
→

Phase A — Validation (always runs first)

›

Checks the institution is accredited and course codes are recognized in the BU catalog

›

Checks all courses have grades, credits, and readable codes

❌ Validation fails
Evaluation halted. Student emailed
to provide missing info. Pipeline stops.
✓ Validation passes
Continue to Phase B.
→

Phase B — Recommendation (for unresolved courses only)

›

Searches past decisions for the same institution and course

›

Searches the BU catalog with program context to find the closest match

›

Submits final recommendations: outcome, matched BU course, confidence, rationale per course

›

Agent results merged into the evaluation record alongside engine results

6
Auto-Apply Settled Outcomes AUTO
After both pipeline phases have run, anything definitively settled is applied automatically — no human needed.
→

Equivalency matches with no conflicting past decisions → decision created automatically

→

Deterministic policy outcomes (grade fail, withdrawn, repeat) → decided automatically

→

Conflicting prior decisions (same course decided differently before) → held for evaluator to resolve

Human Review

Any course still unresolved is assigned to the best matching evaluator in the department.
→

Scoring: +3 expertise course match · +2 subject match · +1 evaluated this course before · prefers evaluators under 80% capacity

→

→

Evaluator notified by email + in-app notification

Evaluator opens the course in their queue. They see the engine recommendation, the agent recommendation, and any past decisions side by side.
→

Approve — accepts the recommendation

→

→

Reject — no credit awarded

→

→

Decision recorded. Conflicts flagged to Credit Office.

Credit Posting
9
Credit Office Posts Credits
Credit Office reviews all decisions together and posts transfer credits to the student's record.
→

Checks blockers: unresolved conflicts, missing decisions, deadline status

→

Can return a course to the evaluator for correction before posting

→

Credit posted per course: outcome, matched BU course, units awarded. Posted as transfer grade, does not count toward GPA.

→

→

Knowledge Base Updated KB
Every decision is written back so the pipeline is more accurate next time.
→

Approved course match → equivalency knowledge base updated

→

All outcomes → added to past decisions with evaluator, reason, and date

The learning loop. Next time this exact course comes in from the same institution, the credit engine hits step 2 (equivalency lookup) and resolves it instantly — no agent call, no evaluator, no delay.
